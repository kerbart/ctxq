What it does

Three engines, one index, one process

The index is a single SQLite file next to your workspace. Everything runs on your machine; the embedding server is the only thing you may choose to make remote.

01Lexical first, dense when you plug a model

A global BM25 with identifier-aware weighting is always on. Offline, that is the search. Plug Ollama or an OpenAI-compatible server and cosine joins it. A port, a container, a domain is a BM25 hit either way.

02Live inventories

Built-in collectors for Docker, systemd, listening ports, projects and scripts — or any command's markdown output. Tables are indexed row by row: “which port does X use?” gets the row, not a page.

03Code graph

A built-in extractor for Rust, TS/JS, Python, Go, Java, Kotlin and C#: symbols, callers and callees, bodies on demand, change impact of a diff, doc ↔ code links.

04Office & PDF, natively

.docx, .pptx with speaker notes, .xlsx, .pdf are converted to markdown in-process and chunked like any other document. No Python, no external service.

05Secrets stay out

Every file is scanned before chunking and embedding. A file holding a key is quarantined — never indexed, never served — and listed by status.

06Pluggable stores

Local by default. Attach to Qdrant, federate other read-only stores or another ctxq instance, weight and merge their results.

How it fits

command output        ─► markdown              │                                  ├─► fusion α ─► caps ─► MCP / daemon / CLI
code                  ─► symbols + call graph  ┘   vectors ─► local | qdrant | peer ┘

Documents

Markdown, Word, PowerPoint (speaker notes included), Excel and PDF are converted to markdown in-process, then cut by H2/H3 headings. Each chunk keeps its breadcrumb (document > section), so the path and the title are searchable too. Tables and inventories are indexed one row per chunk. A file whose hash and mtime are unchanged is never re-read: sync is incremental.

Code

A generic lexer, tuned per language by a small table, feeds a scope tree and per-language declaration recognizers. No full AST: just what navigation needs. Output: symbols with their qualified name and body, calls resolved through imports, doc comments attached to the symbol that follows, and doc ↔ code links.

Ranking

A global BM25 (k1 1.5, b 0.75) plus dense cosine: cosine + α · bm25 / bm25max. Identifiers get a higher α. With the built-in hash embedder, α is raised so BM25 leads — the hash is a weak rerank, not a neural model. Results are capped and always carry their source and line range.

Measured, not guessed

A 100-question golden set, drawn from a real private workspace and kept out of the repository, is the number below. A smaller public set over ctxq's own docs ships in eval/public/ and runs in CI. Agent surface

Designed for the model reading it

Stable result schema, bounded output everywhere, one MCP server named ctxq. The same operations exist on the CLI and on the daemon's HTTP API.

Quick start

Two commands

  1. Set up a workspace

    $ ctxq setup   # from a project — indexes, then registers MCP

    Claude Code, Codex, Cursor, VS Code, Zed, Windsurf… detected and configured. Codex is picked up when ~/.codex/ exists — restart it, then /mcp. Do not run ctxq in the Codex shell (the sandbox blocks it); the MCP tools are the path that works. You never start the MCP server yourself — the editor runs ctxq mcp in the background.

  2. Ask it yourself

    $ ctxq search "how do I deploy the api?"
$ ctxq search "retention policy" --tag legal --type pdf --json

    The first search starts a daemon that keeps the index warm and re-syncs docs every 60s (inventories every 5 min). Offline, BM25 leads. For neural semantic search, point it at an embedding server below.

Configuration

One ctxq.toml, nothing machine-specific in the code

Put a ctxq.toml at the root of the workspace (or point $CTXQ_CONFIG at one). With no file at all, ctxq works offline: BM25 plus a hash embedder. For neural semantic search, pick one of the two:

A local or LAN server — no credentials

[embed]
backend = "ollama"
urls = ["http://gpu-box:11434", "http://localhost:11434"]   # tried in order
model = "qwen3-embedding:0.6b"

An API with a key — OpenAI or any compatible server

[embed]
backend = "openai"                    # also LM Studio, vLLM, TEI, llama.cpp…
urls = ["https://api.openai.com"]
model = "text-embedding-3-small"
api_key_env = "OPENAI_API_KEY"        # the NAME of a variable, not the key
$ export OPENAI_API_KEY="sk-..."      # in your shell profile or your secret manager

The key never goes in the file. ctxq.toml can be committed and shared; the key stays in your environment. It is sent as Authorization: Bearer to the embedding server only. Same pattern for Qdrant and federated peers (api_key_env) and the daemon's HTTP API (http_token_env). Remote embedding is never implicit and always bounded (concurrency, batch). CTXQ_* variables override the file, --embeddings overrides both; every key is documented in ctxq.example.toml.

Install

Prebuilt binaries, checksum-verified

One line installs a verified binary and puts ctxq on your PATH. No compiler, no root, no cargo fallback.

Linux & macOS

$ curl -fsSL https://ctxq.dev/install.sh | sh && . "$HOME/.ctxq/env"

Copy the whole line. . ~/.ctxq/env is what puts ctxq on this shell's PATH — a pipe cannot export to its parent. The installer also writes that source into your shell rc, so new terminals just work. Then, from a project directory: ctxq setup. Windows: use WSL. Binaries come from GitHub Releases (this site mirrors them). Linux x86_64 is musl-static.

From source

Source of truth: github.com/kerbart/ctxq.

$ cargo install --git https://github.com/kerbart/ctxq.git --locked

Override the destination with CTXQ_BINDIR. Archives: GitHub and /releases.
